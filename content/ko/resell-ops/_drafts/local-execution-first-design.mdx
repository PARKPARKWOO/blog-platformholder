셀러 도구를 결제하기 직전, 신중한 사람일수록 같은 질문 앞에서 멈춥니다.

**"이 프로그램은 내 계정 정보를 어디에 두는가."**

기능 소개 페이지에는 대개 그 답이 없습니다. "안전하게 보관합니다"라고만 적혀 있고, 어디에 어떤 형태로 두는지는 나오지 않습니다. 저희는 이 질문을 제품의 첫 설계 결정으로 다뤘습니다. 그 판단 근거와, 그 선택 때문에 포기한 것들을 그대로 적어둡니다.

<Callout type="note" title="이 글의 요약">
- 계정을 서버에 맡기는 대행 모델은 사고 시 영향 범위가 사용자 전체로 번집니다
- 그래서 실행 주체를 **사용자 컴퓨터**에 두기로 했습니다
- 대신 컴퓨터가 꺼져 있으면 아무것도 진행되지 않습니다. 무인 운영이 아닙니다
- "아무것도 수집하지 않는다"는 사실이 아니라서 쓰지 않습니다. 저장 항목을 표로 적어뒀습니다
- 아직 설치할 수 있는 배포물이 없습니다. 지금 글로 남기는 건 설계 판단뿐입니다
</Callout>

## 대행 모델이 편한 이유, 그리고 남는 부담

**서버가 사용자 대신 채널에 접속하는 모델은 사용자 경험이 압도적으로 편합니다.** 설치가 필요 없고, 컴퓨터를 꺼도 돌아가고, 브라우저만 있으면 어디서든 확인됩니다. 이 장점은 진짜입니다.

문제는 그 편의의 대가가 전부 자격증명 쪽에 쌓인다는 점입니다.

1. **보관 표면이 생깁니다.** 서버가 대신 로그인하려면 비밀번호나 세션 쿠키를 어떤 형태로든 보관해야 합니다. 암호화해도 "복호화할 수 있는 곳"이 서비스 안에 존재합니다.
2. **세션이 사용자 손을 떠납니다.** 로그인 상태가 사용자 기기가 아닌 곳에 놓이면, 무엇이 언제 실행됐는지 사용자가 직접 확인할 방법이 줄어듭니다.
3. **사고의 폭발 반경이 전체가 됩니다.** 한 대의 서버가 침해되면 영향 범위는 그 서비스를 쓰는 모든 사용자의 채널 계정입니다. 개인 사용자가 아무리 조심해도 자기 몫이 아닌 위험을 함께 집니다.

개인 리셀러에게 채널 계정은 재고와 정산 기록이 붙어 있는 자산입니다. 저희는 그 자산의 위험을 저희 서버에 모으는 쪽을 택하지 않기로 했습니다.

## 그래서 실행 위치를 사용자 컴퓨터로 정했습니다

**실행 주체는 사용자 컴퓨터에서 도는 데스크톱 프로그램이고, 서버는 원장과 상태 관제만 맡는 구조로 설계했습니다.** 저희 쪽 문서에서 이 결정을 local-execution-first라고 부릅니다.

구체적으로 이렇게 갈랐습니다.

- 채널 로그인과 보안 확인(OTP·캡차 등)은 **사용자가 보이는 브라우저에서 직접** 합니다. 저희가 대신 처리하지 않습니다.
- 장치를 여는 열쇠는 프로그램이 사용자 컴퓨터에서 생성한 Ed25519 키쌍입니다. 개인키는 OS 보안 저장소(macOS Keychain / Windows DPAPI)에 암호화해 두고, **서버로 보내는 것은 공개키뿐**입니다.
- 서버 쪽 장치 테이블에도 공개키만 들어갑니다. 채널 비밀번호·쿠키·세션을 담는 자리를 아예 만들지 않았습니다.
- 활성화 키(256-bit 난수)는 원문을 저장하지 않고 버전이 붙은 HMAC 다이제스트만 남깁니다.

서버 워커에서 실행하는 경로는 열거형과 인터페이스로 예약만 해두고 상용 범위에서 꺼둔 상태입니다. 나중에 편의를 이유로 슬쩍 켜지는 일을 막으려면, 처음부터 기본값이 꺼짐이어야 한다고 봤습니다.

## 이 선택으로 포기한 것

설계 결정은 얻는 것만 적으면 광고가 됩니다. 포기한 것을 같이 적습니다.

- **컴퓨터가 꺼져 있으면 아무 작업도 진행되지 않습니다.** 무인 24시간 운영이 아닙니다. 이건 버그가 아니라 이 설계의 정의입니다.
- **설치와 업데이트 부담이 남습니다.** 브라우저만 열면 끝나는 서비스보다 시작 비용이 큽니다.
- **지원 대상이 좁아집니다.** Windows 11 64-bit, Windows 10 22H2(ESU 한정), macOS 13+ 로 한정했습니다. 모바일만 쓰는 분은 대상이 아닙니다.
- **배포 자체가 큰 과제가 됩니다.** Windows 코드 서명, macOS Developer ID·notarization이 끝나야 설치할 수 있는 물건이 나옵니다. 저희는 **아직 이 단계를 끝내지 못했습니다.**
- **지금 운영 프로필에서는 에이전트 경로가 통째로 막혀 있습니다.** 서명 검증기가 아직 구현되지 않았고, 미구현 상태에서 열어두는 대신 요청을 전부 거절하도록(fail-closed) 두었습니다. 그래서 현재 상태는 "느슨하게 동작"이 아니라 "동작하지 않음"입니다.

## 서버가 저장하는 것과 저장하지 않는 것

**"아무 정보도 수집하지 않는다"는 문장은 사실이 아니라서 쓰지 않습니다.** 정확한 경계는 아래와 같습니다.

| 서버에 저장하지 않는 것 | 서버에 저장하는 것 |
|---|---|
| 채널 로그인 비밀번호 | 라이선스 식별자(회원가입 없이 등록하는 공개 ID) |
| 채널 세션 쿠키·로그인 상태 | 장치 공개키와 장치 메타데이터(OS·버전 등) |
| 장치 개인키(OS 보안 저장소에만 보관) | 작업 원장(언제 어떤 작업이 생성·완료·실패했는지) |
| 활성화 키 원문 | 활성화 키의 HMAC 다이제스트 |
| 오류의 원문 메시지·스택·파일 경로 | 오류의 분류·심각도·시점·sha256 지문 |
| 정산 파일의 원본 셀 값 | — |

오류 진단을 원문 없이 하도록 만든 이유도 같습니다. 진단 데이터에 원문 메시지와 경로가 들어가기 시작하면, 거기에는 결국 상품명·주문번호·파일 경로 같은 것이 섞여 들어옵니다. **원문을 안 받으면 진단이 만능일 수 없습니다.** 대신 사용자가 예상하지 못한 데이터가 나가는 일도 없습니다. 저희는 후자를 택했습니다.

## 1단계를 "채널로 나가는 요청 0"으로 잡은 이유

**출시 1단계의 범위는 채널 서버로 나가는 요청이 0인 지점까지로 잡았습니다.**

커넥터는 아무 코드나 실행되지 않고, 승인된 릴리스 목록과 완전히 일치할 때만 실행되도록 게이트를 **설계했습니다.** 설정에 올려 둔 승인 릴리스는 현재 하나뿐이고, 그 하나는 **네트워크 송신이 꺼진 상태로 고정**해 두었습니다. 문제가 생기면 기능 단위로 즉시 차단하는 스위치도 함께 설계했습니다. 다만 앞서 적었듯 서명 검증기가 미구현이라 운영 프로필에서는 이 경로가 전부 거절(fail-closed)되므로, 이 게이트가 실제로 무언가를 실행하며 돌아가고 있는 상태는 아닙니다.

그래서 1단계에서 하려는 일은 이만큼입니다 (🚧 아직 설치할 수 있는 배포물이 없어 지금 실행해 볼 수는 없습니다).

- 사용자가 **직접 채널에서 내려받은 파일**을 프로그램에서 선택합니다
- 그 파일을 **사용자 컴퓨터 안에서** 검증합니다 — 인코딩, 헤더 구조, 중복된 주문 식별자, 합계 불일치 등
- 상한은 파일 5 MiB, 데이터 10,000행이고, 판정하는 문제 유형은 36가지입니다
- 검증 결과에는 **원본 셀 값을 담지 않습니다.** 문제 코드·범위·행 번호·열 이름만 남깁니다

자동으로 주문을 긁어오지 않습니다. 정산 내역을 대신 내려받지도 않습니다. 채널에 요청을 보내지 않기 때문입니다. 느리고 답답한 1단계지만, 계정 위험이 가장 낮은 지점부터 시작하는 것이 맞다고 판단했습니다.

<Callout type="warning" title="검증된 파일이 원장에 들어가는 단계는 아직입니다">
현재 설계된 범위는 **로컬 검증까지**입니다. 검증된 데이터를 재고·정산 원장에 적재하는 기능은 만들고 있는 중이고, 아직 동작하지 않습니다.
</Callout>

## 만들지 않기로 한 것

범위를 좁히는 글이니 무엇을 안 만드는지도 분명히 적습니다. 아래는 전부 제품 사양에 비목표로 적혀 있습니다.

- 자동 구매·자동 매입·원클릭 구매 — **만들지 않습니다.**
- 드롭 응모·래플 자동 참여 — **만들지 않습니다.**
- 재고 선점·물량 확보 — **만들지 않습니다.**
- 탐지 회피·프록시 회전·자동화 흔적 은폐 — **만들지 않습니다.**
- CAPTCHA 자동 해결·OTP 자동 입력·로그인 대행 — **만들지 않습니다.**
- 여러 계정 동시 운영·계정 대리 로그인 — **만들지 않습니다.**

다루는 범위는 **이미 판매자 본인이 하고 있는 운영 업무**입니다. 재고 기록, 주문 정리, 발송 관리, 정산 대사, 손익 계산입니다.

그리고 이렇게 범위를 좁혀도 **계정이 안전하다고 보장할 수는 없습니다.** 채널 약관상 자동화 접근이 제한될 수 있고, 그 판단과 위험은 사용자에게 귀속됩니다. 이 문장을 지우지 않는 것이 저희가 할 수 있는 정직한 최선입니다.

| 실행 모델·자격증명 격리 설계 | 🚧 코드 작성, 배포 전 |
| 장치 연결 상태·작업 수명주기 | 🚧 코드 작성, 운영 프로필에서 차단(fail-closed) |
| 회원가입 없는 라이선스·지원 문의·오류 진단 | 🚧 코드 작성, 배포 전 |
| 로컬 파일 검증(1단계) | 🚧 검증까지 설계 완료, 원장 적재 미구현 |
| **상품·재고·주문·정산·손익 원장(제품의 본체)** | 🚧 **전량 미구현** |
| 다중 채널 통합·재고 할당 | 📅 설계 문서만 |
| 서명된 설치 배포물·자동 업데이트 | 📅 미구현 = **설치할 수 있는 물건 없음** |

채널 연동은 KREAM → 무신사 SOLDOUT → StockX 순으로 **계획**하고 있습니다. 코드 기준으로 현재 첫 번째는 로컬 파일 검증 1단계까지고(🚧 작성 중이며 배포·실행은 불가), 두 번째는 채널이 제공하는 내보내기 양식을 확보하지 못해 거절 상태이며, 세 번째는 공개 API 사용 승인을 기다리는 중이라 코드가 없습니다. **세 곳 모두와 제휴 관계가 없습니다.**

출시 시점은 날짜로 약속하지 않겠습니다. 조건은 공개합니다 — 원장 코어와 출시 선행 게이트(비제휴 고지, 개인정보 흐름표)가 끝나야 합니다.

## 그래서 무엇을 만들고 있나

정리하면 저희는 매입·재고·주문·정산·손익을 하나의 원장에 모으는 개인·소규모 리셀러용 도구(Resell Ops)를 만들고 있습니다. 실행은 사용자 컴퓨터에서 이뤄지고, 서버는 원장과 상태 관제만 맡고, 채널 비밀번호·쿠키·세션은 서버에 저장하지 않는 구조입니다. **아직 설치할 수 있는 배포물이 없고 원장 기능도 개발 중이라, 지금 쓸 수 있는 것은 없습니다.** 대신 무엇을 어떻게 만드는지는 이렇게 계속 공개합니다.

준비되면 가장 먼저 알려드리겠습니다. 런칭 알림과 격주 개발 기록은 아래 오픈채팅에서 받으실 수 있습니다.

## 자주 묻는 질문

**셀러 프로그램에 채널 계정 비밀번호를 입력해도 되나요?**
판단은 사용자 본인의 몫이지만, 최소한 세 가지는 확인하는 편이 좋습니다. 비밀번호와 세션이 어디에 저장되는지, 서버가 사용자를 대신해 채널에 로그인하는지, 그 서버가 침해됐을 때 영향 범위가 어디까지인지입니다. Resell Ops는 채널 비밀번호·쿠키·세션을 서버에 저장하지 않는 구조로 설계했지만, 아직 개발 중이라 검증할 배포물이 없습니다.

**로컬에서 실행되는 프로그램은 클라우드 서비스와 무엇이 다른가요?**
실행 주체가 다릅니다. 클라우드 대행 모델은 사업자 서버가 사용자 계정으로 작업을 수행하고, 로컬 실행 모델은 사용자 컴퓨터에서 수행합니다. 대신 컴퓨터가 꺼져 있으면 아무것도 진행되지 않고, 설치·업데이트·OS 호환 부담이 사용자와 개발자 양쪽에 남습니다.

**리셀 자동화 도구를 쓰면 채널 계정이 정지될 수 있나요?**
가능성을 부정할 수 없고, 어떤 도구도 안 된다고 보장할 수 없습니다. 채널 약관상 자동화 접근이 제한될 수 있으며 그 판단과 위험은 사용자에게 귀속됩니다. 저희는 구매 자동화·드롭 응모·재고 선점·탐지 회피·CAPTCHA/OTP 처리를 만들지 않고, 출시 1단계는 채널로 나가는 요청이 0인 범위로 잡았습니다.

**Resell Ops는 어떤 채널의 공식 서비스인가요?**
아닙니다. 저희는 어떤 채널과도 제휴·파트너 관계가 없고, 어느 채널의 승인도 받지 않았습니다. 판매자 본인이 자기 판매 기록을 정리하는 것을 돕는 독립 도구를 만들고 있습니다.

**지금 설치해서 써볼 수 있나요?**
아직 없습니다. Windows 코드 서명과 macOS Developer ID·notarization이 완료되지 않아 설치할 수 있는 배포물 자체가 존재하지 않습니다. 재고·주문·정산 원장도 개발 중입니다. 준비되면 이 블로그와 오픈채팅에서 먼저 알리겠습니다.
